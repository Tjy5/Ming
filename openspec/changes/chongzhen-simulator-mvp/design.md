## Context

全新项目，无现有代码。目标用户零编程基础，需要AI辅助完成全部开发。项目定位为MVP——先跑通核心游戏循环，再迭代打磨。

技术约束：
- 前端：React + TypeScript + Vite（生态成熟，组件化开发）
- 后端：Python + FastAPI（异步支持好，AI库生态丰富）
- 存储：SQLite（零运维，单文件部署）
- AI：抽象Provider接口，MockProvider优先，真实LLM后接入

## Goals / Non-Goals

**Goals:**
- 完整的政令→数值变化→AI叙事→界面更新循环
- 确定性规则引擎保证数值可复现
- AI叙事与数值变化严格一致
- 操作后2~3秒内响应（含AI调用）
- 存档/读档支持中断续玩
- MockProvider可零配置运行完整游戏

**Non-Goals:**
- 多人对战
- 音效/音乐/动画特效
- 移动端适配
- 复杂外交系统/详细人物系统/科技树
- 历史100%还原（允许合理戏说）
- 生产级部署（MVP阶段本地运行即可）

## Decisions

### D1: 数值计算与AI叙事分离
- 选择：规则引擎（Python代码）计算所有数值变化，AI仅基于数值delta生成文本
- 替代方案：让AI同时决定数值和叙事
- 理由：AI输出不确定性高，数值由代码控制可保证一致性和可复现性。AI幻觉不会破坏游戏平衡

### D2: 操作触发式回合制
- 选择：每道政令推进1个月游戏时间，无"结束回合"按钮
- 替代方案：传统回合制（攒多个操作后统一结算）
- 理由：即时反馈感更强，符合"2~3秒看到变化"的体验目标。简化状态管理

### D3: AI Provider抽象层
- 选择：定义统一接口，实现MockProvider/OpenAIProvider/ClaudeProvider/OllamaProvider
- 理由：用户尚未决定AI服务，抽象层允许随时切换。MockProvider保证开发阶段零依赖

### D4: 前后端REST通信
- 选择：REST API（非WebSocket）
- 替代方案：WebSocket实时推送
- 理由：MVP阶段请求-响应模式足够，每次政令一个HTTP请求。WebSocket增加复杂度但无明显收益

### D5: SQLite单文件存储
- 选择：SQLite存储存档和游戏配置
- 替代方案：PostgreSQL / JSON文件
- 理由：零运维，单文件便于备份和迁移。MVP数据量极小，SQLite性能绰绰有余

### D6: 自由输入双阶段处理
- 选择：AI先将自然语言解析为结构化政令JSON，再走规则引擎
- 替代方案：AI直接返回数值变化
- 理由：复用规则引擎保证数值一致性。解析失败时可提示玩家重新输入

## Risks / Trade-offs

- [R1] AI响应延迟可能超过3秒目标 → MockProvider无延迟；真实LLM可用流式输出+前端loading动画缓解
- [R2] 自由输入解析准确度不足 → 限定解析输出为已知政令类型枚举；无法解析时提示玩家选择固定按钮
- [R3] 规则引擎平衡性难调 → 初始数值参考历史文献设定，后续通过玩测迭代调整
- [R4] 历史细节准确性 → MVP阶段以游戏性优先，标注"本游戏含艺术加工"
- [R5] 用户零基础维护困难 → 提供一键启动脚本，前后端统一启动
