# 调研 05：缺点教训清单（Ming 应规避）

- **日期**：2026-08-07
- **用途**：为 Ming（《元末纪事》）提供反面清单。每条附来源 URL 与"对 Ming 的启示"。

## 教训 1：商业模式——"买断 + 按量内购"直接引爆差评

- **事实**：48 元本体之外还要买 token，"3 个回合就要 20 块"成为社区梗；"steam评论区第一页除了个别几楼之外都在骂"；评论区"充满了恶评和退款tag"；首月未退款销量仅 4000+ 份（VGI 统计）。玩家预期是"48 元买个游戏框架"，官方自定价出售 token 被视作二道贩子。
- **来源**：https://www.gamersky.com/news/202605/2142683.shtml；https://zhuanlan.zhihu.com/p/2048384535696500060
- **对 Ming 的启示**：若走本地模型（自备 Key/离线）路线则天然规避；若走云端 API，必须前置设计成本策略——免费额度充足、成本透明化、或包月/包年（Steam 社区玩家明确表示"包月乃至包年的物美价廉的服务选择，玩家想必更容易接受"）。**绝不可出现"先买断后内购"的感知**（TapTap 标题原文"开创单机游戏坏先河！先购买后内购模式惨遭差评"）。

## 教训 2：AI 成本 vs 体验的跷跷板必须提前设计

- **事实**：快速模式省成本但幻觉多、体验崩；专家模式质量好但 token 消耗 4 倍、几乎不可能白嫖通关。制作人自述："想要保持体验的连贯性，等待不能超过 2 分钟，要求输出至少 80-120 token/秒（主流 50-60/秒）"——成本与质量不可兼得。
- **来源**：https://zhuanlan.zhihu.com/p/2042377430527206187；https://www.pingwest.com/a/313764
- **对 Ming 的启示**：模型选型时把"效果/成本/速度不可能三角"写进架构决策；可借鉴其多级模型分工（L1044："诏书润色、奏折生成、记忆管理……适合使用轻量模型"）——重活给强模型、边缘任务给轻模型，但**核心推演质量不能以玩家体验为代价**。

## 教训 3：长上下文记忆混乱——"准奏串题"

- **事实**：对话积累后点击"准奏"自动拟旨，可能输出"开始建设工厂""拨20万两开仓赈灾"等与当前议题无关的旧话题；多回合政令无法自动持续，玩家必须每回合提醒 AI"想起来"。
- **来源**：https://zhuanlan.zhihu.com/p/2042377430527206187
- **对 Ming 的启示**：必须有**显式的"执行中政策/任务追踪"系统**（结构化状态，而非全靠上下文）；其圣旨总结 prompt（200 字内+只总结本回合+适量遗忘）是缓解手段，但根治要靠状态机把"正在执行的政策"持久化到游戏数据里。

## 教训 4：AI 幻觉破坏策略游戏的可解释性

- **事实**："文本说政策执行了，面板数据却没变；大臣被罢免了，下一回合还在朝堂发言；战争结果刚写完，下一次推演又被改口"；已死大臣仍能对话，AI 用"死者苏生""假死辞官"找补。"玩家想要不可预测，但不想要不可靠"——策略游戏最核心的是可解释性（我做了什么→为什么这样反馈→数值为何变化）。
- **来源**：https://zhuanlan.zhihu.com/p/2048384535696500060；https://zhuanlan.zhihu.com/p/2042377430527206187
- **对 Ming 的启示**：**文本叙事与数值面板必须同源**（推演结果直接落库再渲染文本，禁止文本层自由发挥）；对"已死/被免/囚禁"等状态要有硬性校验层（见教训 7）；随机性可以是魅力，但不能让玩家无法判断规则。

## 教训 5：史实硬伤与"阴谋论"设定引发核心玩家不满

- **事实**：知乎问题题干点名"游戏设定过于阴谋论，缺少明史专家参考"；AI 在崇祯登基初年说出"大顺"（李自成崇祯十七年才建的国号）；文案模板化（"不是XX……而是XXX！"八股句式疲劳）。
- **来源**：https://www.zhihu.com/question/2004918435499501395；https://www.3dmgame.com/original/3745943.html
- **对 Ming 的启示**：历史模拟游戏的历史正确性是口碑底线——**引入明史/元史专家审校或事实核查清单**；prompt 明确年代约束（"当前年份/年号"每次注入）；对"不是……而是……"类模板句式做去八股化提示。Ming 题材（元末）史实争议点更多（朱元璋出身、小明王、郭子兴等），更要谨慎。

## 教训 6：发售节奏与舆情管理

- **事实**：公测期有预期管理（玩家"有在期待、有在耐心提建议"），但发售时收费实锤后舆情失控；官方被批"画饼"（API/创意工坊"巨饼无限期"）；官方群禁讨论问题加剧不信任（社区指控，存疑）。
- **来源**：https://www.gamersky.com/news/202605/2142683.shtml；https://steamcommunity.com/app/4304230/discussions/0/572666202100372808/
- **对 Ming 的启示**：收费/成本相关承诺必须售前说明白（"在发布游戏之前，制作组曾经发布过更新公告，表示在购买游戏之后，会对token进行额外收费"——他们做过预告但仍翻车，说明光预告不够，需要**定价机制本身就合理**）；保持官方沟通渠道开放。

## 教训 7：状态一致性校验缺失（世界的"记忆"不可靠）

- **事实**：世界状态与文本叙事脱节、人物生死状态失效、"AI 找补"式圆场（魔法卡死者苏生）——说明其"状态保留层"未能完全约束生成内容。
- **来源**：https://zhuanlan.zhihu.com/p/2042377430527206187；https://zhuanlan.zhihu.com/p/2048384535696500060
- **对 Ming 的启示**：为每个 Agent/人物的生死、官职、阵营做**硬状态源**（数据库），LLM 输出必须经状态校验（可参考其 benchmark 思路：状态修改成功率 99% 阈值），不一致时强制重试或修正，而非让模型自行"找补"。

## 教训 8：开放 API 是双刃剑——体验一致性风险

- **事实**：官方承诺开放自定义 API 缓解收费矛盾，但社区已预见风险："不同模型接入所造成的对于游戏体感的不同，也会造成游戏正负面评介不平衡的现象爆发"；被类比为"早期PC游戏的显卡兼容时代——能跑，但每个人跑出来的效果可能都不一样"。
- **来源**：https://steamcommunity.com/app/4304230/discussions/0/572666202100372808/；https://zhuanlan.zhihu.com/p/2048384535696500060
- **对 Ming 的启示**：若支持玩家自定义模型，需提供**模型适配层 + 质量分级标识**（不同模型标注推荐度/兼容性），并保证官方默认配置体验统一。

## 教训 9：服务稳定性（模型厂商不可抗力）

- **事实**："DeepSeek 整体挂了十几分钟，确实对我们来说是不可抗力"；发售期间存在"【服务端异常】闪退"类投诉；千人同时在线时算力压力。
- **来源**：https://www.pingwest.com/a/313764；https://steamcommunity.com/app/4304230/discussions/0/572666202100372808/
- **对 Ming 的启示**：多模型容灾（Ming 已有 provider 体系与 fallbacks.py——方向正确），关键路径需降级策略（本地兜底/重试/排队提示），不能让模型厂商波动直接变成玩家闪退。

## 教训 10：商业结果与热度严重倒挂（实验品的宿命）

- **事实**：讨论度极高、留存惊人（75.1% 次日留存/日均 7 小时），但首月未退款销量仅 4000+ 份（约 20 万元）——"一边挨骂，一边停不下来"的玩家并没有转化为收入；制作人自认"整体上来讲不可能赚钱"。上线仅一年内 Steam 好评率持续在 54%-58% 低位。
- **来源**：https://zhuanlan.zhihu.com/p/2048384535696500060；https://zhuanlan.zhihu.com/p/2042377430527206187
- **对 Ming 的启示**：**留存不等于付费意愿**；验证 AI 游戏玩法成立之后，商业闭环（内容更新、DLC、订阅、社区共创）要尽早规划，不能赌"先做出来再说"。
